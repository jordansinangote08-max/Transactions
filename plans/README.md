# Animation plans

Generated by the `improve-animations` skill (`plan <description>` mode, skipping the full audit — these two came directly out of a `find-animation-opportunities` sweep) at commit `2e51401`. Each plan is self-contained — see the individual file for exact current code, target code, and a feel-check verification section.

| # | Title | Severity | Category | Status |
|---|---|---|---|---|
| [001](001-history-item-entrance.md) | Animate the entrance of a newly-added transaction in the history list | LOW | Missed opportunity / Preventing a jarring change | N/A — target is dead markup, see plan |
| [002](002-logo-selector-stagger.md) | Stagger the logo choices when the card editor first opens | LOW | Missed opportunity / Delight | DONE |

## Recommended execution order

Either order works — the two plans touch completely disjoint functions (`renderLogs`/the transaction-save handler vs. `renderLogoSelector`/`updateLogoPreview`/`openCardEditor`) and share no state. Apply and feel-check one at a time simply to keep each diff easy to review in isolation, not because of any real dependency.

## Dependencies between plans

None. Both plans do share one convention worth keeping consistent if you do both: the `is-entering` (from-state) / `is-settled` (triggers the transition) two-class split, and the `void element.offsetWidth` force-reflow idiom already established by this repo's `revealOverlay()` helper. Neither plan introduces a new pattern — both extend the existing one.

## Notes

- Both plans were scoped directly from the `find-animation-opportunities` report rather than a full `improve-animations` audit — no other findings were surveyed alongside these two.
- Both are LOW severity / additive polish, not fixes for broken motion. Skipping either (or both) leaves the app exactly as functional as it is today.
- **001 turned out to target dead code.** `#logs`, the container `renderLogs()` renders into, is `hidden` in the markup and never unhidden anywhere — the history list was superseded by the Google Sheets sync and is not reachable by any user action. Implemented and Playwright-verified the CSS/JS exactly as specced to confirm the technique itself was sound (it is — proven via an isolated repro), then reverted it, since animating an element no user can ever see isn't a real fix. See the plan file for full detail. If the history list is ever restored, the plan's code is preserved there and can be reapplied as-is.
- **002 shipped**, with two bugs the plan didn't anticipate caught and fixed during verification: a call-order issue (`updateLogoPreview(true)` ran before `revealOverlay()` unhid the modal, so the stagger completed inside a `display:none` subtree with no visible motion) and an event-listener footgun (`updateLogoPreview` used directly as an `input` listener meant the `InputEvent` object satisfied the `animate` parameter, re-staggering on every keystroke). Both are detailed in the plan file's implementation notes.
